## 2. 공용 타입

```sql
-- 투자 성향 프로필. F03(추천 결과)과 F05(시뮬레이션 입력)가 같은 어휘를 씁니다.
--   F03: app/frontend/js/views/portfolioGuide.js:2,13,25
--   F05: app/backend/routers/quant.py:67~69, 검증 패턴 quant.py:51
create type portfolio_profile as enum ('stable', 'balanced', 'growth');

-- F03 설문 3문항. 값은 portfolioGuide.js:95~97 의 <option value> 실측입니다.
create type invest_goal    as enum ('growth', 'balance', 'protect');
create type invest_horizon as enum ('short', 'medium', 'long');
create type risk_appetite  as enum ('low', 'medium', 'high');

-- F04 비교 기간. 검증 패턴 app/backend/main.py:1106
create type combination_period as enum ('3mo', '6mo', '1y', '2y');

-- 거시지표 출처·주기. 4.8절 macro_series 에서 씁니다 (CN-044).
--   kosis 는 통계표가 아직 미정이지만, 나중에 ALTER TYPE 을 하지 않으려고 미리 넣습니다.
create type macro_source    as enum ('ecos', 'kosis', 'fred');
create type macro_frequency as enum ('daily', 'monthly', 'quarterly', 'annual');
```

> **enum 과 CHECK 중 enum 을 골랐습니다.** 이 5개는 프론트 `<option>`·백엔드
> `pattern=` 양쪽에 이미 고정돼 있어 값이 늘어날 일이 드뭅니다. 대신 값을 추가하려면
> `ALTER TYPE … ADD VALUE` 가 필요하다는 대가를 집니다. 값이 자주 바뀌는 축이라면
> CHECK 가 나았을 겁니다.

**주의 — `invest_goal` 의 `balance` 는 오타가 아닙니다.**
`portfolioGuide.js:95` 의 실제 값이 `balance` 이고,
프로필 쪽(`portfolio_profile`)은 `balanced` 입니다. **두 어휘가 실제로 다릅니다.**
통일하고 싶다면 프론트 `<option value>` 를 먼저 고쳐야 하며, 그건 스펙 변경이라
[CN-022](../00-index/변경이력.md#cn-022) 로 올려 두었습니다.

### 4.3 `recommendation_item` — 추천 자산 배분 라인

`PROFILES[*].items` (`portfolioGuide.js:5~10,17~23,29~35`) 를
**그 시점 값으로 스냅샷** 저장합니다. 근거는 [`ERD.md` 2.1절](ERD.md#21-f03-의-백엔드화가-이-erd-의-핵심).

| 컬럼 | 타입 | 제약 | 설명 |
| --- | --- | --- | --- |
| `id` | `bigint` | PK, identity | |
| `recommendation_id` | `bigint` | NOT NULL, FK → `recommendation(id)` ON DELETE CASCADE | |
| `sort_order` | `smallint` | NOT NULL, `≥ 0` | 화면 표시 순서 |
| `asset_name` | `text` | NOT NULL, `length ≤ 40` | `'글로벌 주식'` 등 |
| `weight_pct` | `smallint` | NOT NULL, `between 0 and 100` | 비중 |
| `explanation` | `text` | NOT NULL, `length ≤ 200` | `'장기 성장 기회를 위한 부분'` 등 |

**제약**

```sql
constraint uq_recommendation_item_order unique (recommendation_id, sort_order)
constraint ck_recommendation_item_weight check (weight_pct between 0 and 100)
```

> **색상(`#22c55e` 등)은 저장하지 않습니다.** `items` 배열의 3번째 원소이지만
> **UI 테마의 관심사**입니다. 다크모드나 색 팔레트를 바꾸면 과거 이력의 색까지
> 손봐야 하는 문제가 생깁니다. 색은 `asset_name` 기준으로 프론트에서 매핑합니다.

**비중 합계 100 은 어떻게 보장하나** — 행 단위 CHECK 로는 불가능합니다.

| 방법 | 판단 |
| --- | --- |
| `DEFERRABLE` 제약 + 트리거 | 정확하지만 이 규모에 과함 |
| **서버 계층에서 검증 후 한 트랜잭션 삽입** | **채택.** 배분표는 서버 상수에서 오므로 입력원이 하나 |
| 뷰로 사후 감시 | 병행. 아래 참조 |

```sql
-- 합계가 100이 아닌 추천을 찾아내는 점검용 뷰 (운영 중 사후 감시)
create view v_recommendation_weight_check as
select recommendation_id, sum(weight_pct) as total
from recommendation_item
group by recommendation_id
having sum(weight_pct) <> 100;
```

**`numeric` 을 쓴 이유** — 수수료·세율은 `0.00015` 같은 값이고, 성과 계산에서
누적 곱셈에 들어갑니다. `float` 의 이진 오차가 재현 검증을 방해할 수 있어
**정확한 10진 저장**을 씁니다. 반면 성과 지표(`sharpe` 등)는 어차피 근사값이라
JSONB 안의 숫자로 둡니다.

**`jsonb` 3개만 예외적으로 허용한 이유**

| 항목 | 필드 수 | 판단 |
| --- | --- | --- |
| `BacktestStats` (`lean-hyundai/hd_core.py:324~336`) | 12 | 지표 정의가 아직 바뀔 수 있음. 전략·벤치마크 2벌이라 컬럼화하면 24개 |
| `PredictionMetrics` (`hd_core.py:135~155`) | 15+ | 〃 |

컬럼으로 펼치면 **한 테이블에 40개 가까운 지표 컬럼**이 생기고, 지표를 하나 추가할
때마다 마이그레이션이 필요합니다. F28 은 B등급이고 실험 성격이므로 **JSONB 로 둡니다.**
대신 자주 정렬·필터할 지표는 **생성 컬럼**으로 꺼냅니다.

```sql
-- 자주 쓰는 지표만 인덱싱 가능한 형태로 승격
alter table backtest_summary
  add column strategy_total_return_pct numeric
    generated always as ((strategy_stats->>'total_return_pct')::numeric) stored,
  add column strategy_max_drawdown_pct numeric
    generated always as ((strategy_stats->>'max_drawdown_pct')::numeric) stored;
```

> **`rows`(일별 예측)·`curve`(일별 자산곡선)는 저장하지 않습니다.** 제약 C-04.
> 검증 구간이 6개월이면 행이 120개 남짓이고 실행마다 쌓이면 500MB 를 위협합니다.
> 입력 11개가 남아 있으므로 재실행으로 복원합니다 ([`ERD.md` 0.2절](ERD.md#02-입력을-저장하면-결과가-재현된다)).

| `chunk_index` | `integer` | NOT NULL, `≥ 0` | 문서 내 순번 |
| `content` | `text` | NOT NULL | 청크 원문 (최대 1,200자) |
| `embedding` | `extensions.vector(768)` | NULL | Gemini `gemini-embedding-001` 절단·정규화 |
| `embedding_hash` | `extensions.vector(384)` | NULL | 폴백용 `_hash_embed` (`rag.py:52`) |
| `embed_method` | `text` | NOT NULL, `in ('gemini','hash')` | 어느 컬럼이 유효한지 |
| `token_count` | `integer` | NULL | 색인 시 실측 (2,048 상한 감시용) |
| `indexed_at` | `timestamptz` | NOT NULL, `default now()` | |

**제약**

```sql
constraint uq_doc_chunk unique (source_doc, chunk_index)
constraint ck_doc_chunk_embedding check (
  (embed_method = 'gemini' and embedding      is not null) or
  (embed_method = 'hash'   and embedding_hash is not null)
)
```

> **벡터 컬럼을 두 개로 나눈 이유.** 차원이 768 과 384 로 **다릅니다.**
> `vector(n)` 은 차원이 타입의 일부라 한 컬럼에 섞을 수 없습니다.
> 폴백이 필요한 근거는 [`ERD.md` 4.3절](ERD.md#43-임베딩--무료-조건에서의-선택).

**인덱스**

```sql
-- 코사인 거리 기준 근사 최근접 탐색
create index idx_doc_chunk_embedding on doc_chunk
  using hnsw (embedding extensions.vector_cosine_ops);
```

| 확인 사항 | 내용 |
| --- | --- |
| 인덱스 차원 한계 | pgvector 는 `vector` 타입 최대 16,000 차원, **인덱스는 2,000 차원까지** ([pgvector README](https://github.com/pgvector/pgvector), 2026-08-09 확인). 768 은 안전, **기본값 3072 는 인덱스 불가** |
| 거리 연산자 일치 | 색인·질의 모두 코사인(`<=>`). Qdrant 설정도 `"distance": "Cosine"` 이었습니다 (`upload_docs_to_qdrant.sh`) — 동작이 바뀌지 않습니다 |
| 이 규모에 인덱스가 필요한가 | **178행이면 순차 스캔으로 충분합니다.** 인덱스는 문서가 늘어날 때를 위한 것이고, 지금은 성능이 아니라 **설계 정합성** 목적입니다 |

**검색 함수** — 프론트에 SQL 을 노출하지 않기 위해 RPC 로 감쌉니다.

```sql
create or replace function match_doc_chunk(
  query_embedding extensions.vector(768),
  match_count int default 5,
  score_threshold float default 0.0
)
returns table (id bigint, source_doc text, chunk_index int, content text, score float)
language sql stable
as $$
  select c.id, c.source_doc, c.chunk_index, c.content,
         1 - (c.embedding <=> query_embedding) as score
  from doc_chunk c
  where c.embedding is not null
    and 1 - (c.embedding <=> query_embedding) >= score_threshold
  order by c.embedding <=> query_embedding
  limit match_count;
$$;
```

> 반환 필드는 현행 `rag.py:86~91` 의 `{score, source_doc, chunk_index, text}` 와
> 이름을 맞췄습니다(`text` → `content` 만 다름). **프론트 `ragChat.js` 의 변경을
> 최소화하기 위해서**이고, 응답 직렬화 단계에서 `content` → `text` 로 되돌립니다.

### 4.8 `macro_series` / `macro_observation` — 거시지표 참조 데이터

**[CN-044](../00-index/변경이력.md#cn-044) 가 남긴 스키마입니다.**
세션 6에서 "거시지표를 DB 에 넣는다" 까지만 정하고 테이블 정의를 미뤘습니다
([`../20-기능명세/04-거시경제.md` 4.5절](../20-기능명세/04-거시경제.md#45-설계-원칙--거시지표는-db-에-넣습니다)).

#### 왜 C-04 의 예외인가

C-04 는 "시세 원본을 DB 에 넣지 않는다" 입니다. 거시지표는 **시세가 아닙니다.**

| 기준 | 시세 (넣지 않음) | 거시지표 (넣음) |
| --- | --- | --- |
| 갱신 빈도 | 초·분 | **일·월** |
| 행 수 | 종목 × 거래일 = 수백만 | **2만 행 미만** (아래 용량 산정) |
| 재조회 비용 | 낮음 (yfinance 무인증) | **쿼터 소모** (ECOS·FRED 는 인증 키) |

[CN-023](../00-index/변경이력.md#cn-023) 이 DART 회사 마스터에 적용한 것과 같은 논리입니다.
하루 1회 로컬 배치로 채우고 **화면은 DB 만 읽습니다.**

#### 왜 테이블을 둘로 나누는가

지표 하나의 **메타(통계표 코드·항목 코드·단위·주기)는 고정**이고
**값만 날짜별로 늘어납니다.** 한 테이블에 합치면 `'722Y001'`·`'연%'` 같은 문자열이
관측치 1만 7천 행에 그대로 복제됩니다. 마스터를 갈라 두면 **출처 코드가 바뀔 때
고칠 곳이 한 행**입니다.

#### `macro_series` — 지표 마스터

| 컬럼 | 타입 | 제약 | 설명 |
| --- | --- | --- | --- |
| `id` | `smallint` | PK, `generated always as identity` | |
| `code` | `text` | NOT NULL, UNIQUE, `length ≤ 40` | 내부 코드. 예: `'KR_BASE_RATE'` |
| `name_ko` | `text` | NOT NULL, `length ≤ 40` | 화면 표시명. 예: `'한국은행 기준금리'` |
| `source` | `macro_source` | NOT NULL | `ecos` / `kosis` / `fred` |
| `source_table` | `text` | NOT NULL, `length ≤ 20` | ECOS 통계표 코드 · FRED `series_id` |
| `source_item` | `text` | NULL, `length ≤ 20` | ECOS 항목 코드. FRED 는 NULL |
| `frequency` | `macro_frequency` | NOT NULL | 적재 주기 |
| `unit` | `text` | NOT NULL, `length ≤ 20` | `'연%'` · `'원'` · `'2020=100'` |
| `available_from` | `date` | NOT NULL | 출처가 제공하는 **최초 관측일** (실측) |
| `is_active` | `boolean` | NOT NULL, `default true` | 배치 대상에서 뺄 때 `false` |
| `updated_at` | `timestamptz` | NOT NULL, `default now()` | 마지막 배치 성공 시각 |

**제약**

```sql
constraint uq_macro_series_source unique (source, source_table, source_item)
```

> **`(source, source_table, source_item)` 에도 UNIQUE 를 겁니다.** `code` 만
> UNIQUE 로 두면 같은 ECOS 통계표를 내부 코드만 바꿔 **두 번 등록**할 수 있고,
> 배치가 같은 값을 두 계열에 쌓습니다.
>
> **NULL 이 섞인 UNIQUE 에 주의합니다.** Postgres 기본 동작에서 `source_item` 이
> NULL 인 행(FRED)은 서로 중복으로 잡히지 않습니다
> ([CREATE TABLE — UNIQUE](https://www.postgresql.org/docs/17/sql-createtable.html), 2026-08-10 확인).
> FRED 계열이 늘어나면 `nulls not distinct` 를 붙이거나 `source_item` 을
> `''` 로 채워야 합니다. **지금은 FRED 계열이 1개라 문제가 되지 않습니다.**

**초기 5행** — 통계표·항목 코드는 **API 실호출로 확인한 값**입니다
([`../20-기능명세/04-거시경제.md` 4.2~4.3절](../20-기능명세/04-거시경제.md#42-ecos--통계표-코드까지-실검증), 2026-08-10 실측).

| `code` | `name_ko` | `source` | `source_table` | `source_item` | `frequency` | `unit` | `available_from` |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `KR_BASE_RATE` | 한국은행 기준금리 | `ecos` | `722Y001` | `0101000` | `daily` | 연% | 1999-05-06 |
| `KR_USD_KRW` | 원/미국달러 매매기준율 | `ecos` | `731Y001` | `0000001` | `daily` | 원 | 1964-05-04 |
| `KR_CPI` | 소비자물가지수 (총지수) | `ecos` | `901Y009` | `0` | `monthly` | 지수 | 1965-01-01 |
| `US_FED_FUNDS` | 미국 연방기금금리 | `fred` | `FEDFUNDS` | NULL | `monthly` | 연% | 1954-07-01 |
| *(KOSIS 보조 지표)* | **(확인 필요)** | `kosis` | **(확인 필요)** | — | — | — | — |

> ⚠ **KOSIS 행은 비워 둡니다.** [CN-044](../00-index/변경이력.md#cn-044) 는 KOSIS 키가
> **살아 있다는 것까지만** 확인했고(주제별 목록 수신), **어느 통계표를 쓸지는 정하지
> 않았습니다.** 통계표를 실호출로 확정하기 전에는 행을 만들지 않습니다.
> `macro_source` enum 에 `kosis` 를 미리 넣어 두어 **스키마 변경 없이** 추가됩니다.
>
> `available_from` 은 **출처가 제공하는 최초 관측일**이고, **우리가 적재하는 시작일이
> 아닙니다.** 적재 시작일은 아래 용량 산정에서 2000-01-01 로 정합니다.

#### `macro_observation` — 관측치

| 컬럼 | 타입 | 제약 | 설명 |
| --- | --- | --- | --- |
| `series_id` | `smallint` | **PK(복합)**, FK → `macro_series(id)` ON DELETE CASCADE | |
| `obs_date` | `date` | **PK(복합)** | 관측일. 월·분기 지표는 **해당 기간의 1일** |
| `value` | `numeric(18,6)` | NOT NULL | 지표 값 |
| `ingested_at` | `timestamptz` | NOT NULL, `default now()` | 이 행을 적재한 시각 |

**제약**

```sql
constraint pk_macro_observation primary key (series_id, obs_date)
```

> **1절 명명 규칙의 "기본키는 `id`" 를 여기서만 어깁니다 — 의도한 예외입니다.**
> `(series_id, obs_date)` 가 **자연키**이고, 이 테이블에서 필요한 유일한 무결성 규칙이
> "한 지표의 한 날짜에 값은 하나" 입니다. 대리키 `id` 를 두면 그 규칙을 지키기 위해
> 어차피 같은 조합에 UNIQUE 를 또 걸어야 하고, **인덱스가 하나 늘 뿐 얻는 것이 없습니다.**
> 이 테이블은 다른 테이블에서 참조되지 않으므로 짧은 FK 대상이 필요하지도 않습니다.
>
> **월·분기 지표의 `obs_date` 를 기간 1일로 고정합니다.** CPI `202607` 은 `2026-07-01`
> 로 적재합니다. 말일로 적으면 "7월 지표" 와 "7월 31일 값" 이 섞이고, 주기가 다른
> 지표를 한 축에 그릴 때 정렬이 틀어집니다. FRED 가 이미 이 규약을 씁니다 —
> `FEDFUNDS` 의 2026년 7월 값이 `2026-07-01` 로 옵니다 (실측 2026-08-10).

**인덱스**

| 인덱스 | 컬럼 | 용도 |
| --- | --- | --- |
| *(PK)* | `(series_id, obs_date)` | 지표별 기간 조회 — F13 의 기본 질의 |
| `idx_macro_observation_date` | `(obs_date)` | **여러 지표를 한 날짜로 가로 조회** — F14 시작값 초기화 |

> 두 번째 인덱스가 필요한 이유는 **F14 때문입니다.** [CN-044](../00-index/변경이력.md#cn-044) 는
> F14 GBM 의 시작값 6쌍을 "F13 의 실제 최근값" 으로 초기화하기로 했고
> ([`../20-기능명세/04-거시경제.md` 2.5절](../20-기능명세/04-거시경제.md#25-v20-조치)),
> 그 질의는 `series_id` 가 아니라 **날짜를 축으로** 여러 계열을 한 번에 읽습니다.
> PK 의 선두 컬럼이 `series_id` 라 PK 만으로는 이 질의를 못 탑니다.

#### 적재 시작일과 용량 산정

**2000-01-01 이후만 적재합니다.**

```
2000-01-01 ~ 2026-08-10 = 달력일 9,719  ·  영업일 추정(×5/7) 6,942
2000-01    ~ 2026-07    = 319 개월
```

| 계열 | 주기 | 행 수 |
| --- | --- | ---: |
| `KR_BASE_RATE` | 달력일 | 9,719 |
| `KR_USD_KRW` | 영업일 (추정) | 6,942 |
| `KR_CPI` | 월 | 319 |
| `US_FED_FUNDS` | 월 | 319 |
| **합계** | | **약 17,300 행** |

행당 약 40 B (`smallint` + `date` + `numeric` + `timestamptz`) 이므로
**0.7 MB 남짓**입니다. 500MB 제약(C-04) 대비 **0.15 %** 이고,
7절 용량표의 `simulation_point`(124 MB) 옆에서는 반올림 오차입니다.

> **`KR_BASE_RATE` 를 달력일로 센 것은 실측 근거가 있습니다.** ECOS `722Y001` 을
> `D` 주기로 부르면 **주말에도 값이 옵니다** — `20260801`(토) · `20260802`(일)
> 둘 다 `2.75` 를 반환했습니다 (2026-08-10 실측,
> [`../20-기능명세/04-거시경제.md` 4.2절](../20-기능명세/04-거시경제.md#42-ecos--통계표-코드까지-실검증)).
> 기준금리는 변경일 사이가 평평한 계단 함수라 달력일로 채워 주는 것이 자연스럽습니다.
>
> 반면 **`KR_USD_KRW` 가 영업일인지 달력일인지는 확인하지 않았습니다 — (확인 필요).**
> 달력일이면 6,942 → 9,719 로 늘어 합계가 약 20,100 행이 되는데, **용량 결론은
> 바뀌지 않습니다** (0.8 MB).
>
> **1964년부터 다 넣지 않는 이유**: 전 구간을 넣으면 약 23,800 행이 됩니다. 용량은
> 여전히 문제가 아니지만, **1964년 환율을 화면에서 쓸 일이 없습니다.** 필요해지면
> `available_from` 이 남아 있으므로 배치를 한 번 더 돌려 소급 적재할 수 있습니다.

#### 배치와 RLS

| 항목 | 방침 |
| --- | --- |
| 갱신 주기 | **하루 1회**. 거시지표는 일·월 단위라 그 이상 부를 이유가 없습니다 |

| 실패 처리 | 계열 단위로 격리합니다. ECOS 가 죽어도 FRED 계열은 갱신되고, `macro_series.updated_at` 으로 **어느 계열이 언제부터 멈췄는지** 드러납니다 |

> 없이 계속 보여줍니다.** 난수 폴백([CN-035](../00-index/변경이력.md#cn-035))과 같은 계열의
> 위험이고, F13 화면에 **"기준일"** 을 상시 표시해 막습니다
> ([CN-057](../00-index/변경이력.md#cn-057) 데이터 출처 배지와 같은 자리).

### 4.9 `dart_company` — DART 회사 마스터

**[CN-023](../00-index/변경이력.md#cn-023) 이 "대응 방향" 으로만 적고 미뤄 둔 스키마입니다.**
[CN-083](../00-index/변경이력.md#cn-083) 이 "결정된 적이 없는데 세 문서가 인용하고 있다" 고
지적했고, **여기서 결정합니다** → [CN-084](../00-index/변경이력.md#cn-084).

#### 왜 C-04 의 예외인가 — 참조 데이터의 **세 번째** 사례

`doc_chunk`(4.7) · 거시지표 2종(4.8) 에 이어 세 번째입니다. 기준은 4.8절과 같습니다.

| 기준 | 시세 (넣지 않음) | 회사 마스터 (넣음) |
| --- | --- | --- |
| 갱신 빈도 | 초·분 | **영업일당 약 5행** (아래 실측) |
| 행 수 | 종목 × 거래일 = 수백만 | **3,981** (실측) |
| 재조회 비용 | 낮음 (yfinance 무인증) | **1회 3,982건** — 일일 한도 20,000 의 **19.9 %** |

**세 번째 열이 결정적입니다.** 거시지표는 "쿼터를 태운다" 는 정성적 우려였지만,
회사 마스터는 **한 번 채우는 데 하루 한도의 5분의 1**이 나갑니다.

#### 실측 — 2026-08-10, DART 호출 3건

`corpCode.xml` 2회 + `company.json` 1회만 썼습니다. `_load_all_listed_details()` 는
**부르지 않았습니다** (부르면 그 자리에서 3,981건이 나갑니다).

> [`외부-데이터소스.md` 2.3절](외부-데이터소스.md#23--한-번의-클릭이-쿼터-수천-건을-태웁니다) 이
> "수천 건" 으로만 적고 **(확인 필요)** 로 둔 값입니다. 한도 20,000 ÷ 3,981 =
> **하루 5.02회**. 서버리스에서 인스턴스가 5개만 떠도 한도가 소진됩니다.
>
> **`corpCode.xml` 에 `corp_eng_name` 이 있는데 코드가 파싱하지 않습니다**
> (`main.py:285~288` 은 4개 태그만 읽습니다). 지금은 `company.json` 의
> `corp_name_eng` 로 덮이므로 **문제가 아니고, 조치하지 않습니다.**

#### 왜 테이블 **하나**인가 — 4.8절과 갈라지는 지점

거시지표는 둘로 나눴는데 여기는 하나입니다. **시계열이 아니기 때문입니다.**

| | `macro_series` / `macro_observation` | `dart_company` |
| --- | --- | --- |
| 값의 축 | 지표 × **날짜** → 행이 계속 늘어남 | 회사 1곳 = **1행**, 갱신은 덮어쓰기 |
| 메타 복제 | 합치면 `'722Y001'` 이 1.7만 행에 복제됨 | 복제될 메타가 없음 |
| 결론 | **분리** | **단일 테이블** |

회사 마스터에는 "고정된 메타" 와 "날짜별로 늘어나는 값" 의 구분이 없습니다.
`company.json` 이 주는 17개 필드가 **전부 그 회사의 현재 상태**이고, 바뀌면 그 행을
덮어씁니다. 나눌 축이 없는데 나누면 **조인만 늘어납니다.**

create unique index uq_dart_company_stock_code

> **UNIQUE 를 부분 인덱스로 건 것은 상장폐지 때문입니다.** 상장이 폐지되면 그 행의
> `is_listed` 를 `false` 로 내리고 **`stock_code` 는 마지막 값으로 남깁니다.**
> 전체 UNIQUE 였다면, KRX 가 그 종목코드를 다른 회사에 재배정할 때 배치가 막힙니다.
> **재배정이 실제로 일어나는지는 확인하지 않았습니다 — (확인 필요).** 확인 전까지는
> 막히지 않는 쪽을 고릅니다. 되돌리는 비용(인덱스 1개 교체)이 작습니다.

**인덱스 — PK 와 위 UNIQUE 둘뿐입니다**

| 인덱스 | 컬럼 | 용도 |
| --- | --- | --- |
| *(PK)* | `(corp_code)` | F23 재무분석의 단건 조회 (`main.py:2586`) |
| `uq_dart_company_stock_code` | `(stock_code) where is_listed` | 종목코드 → 회사 |

> **회사명·주소 검색에는 인덱스를 걸지 않습니다.** F20·F22 는 회사명 부분일치,
> F21 은 주소 부분일치인데(`main.py:331~334,550`) **`%키워드%` 는 btree 를 타지 않습니다.**
> 트라이그램 GIN(`pg_trgm`)이 정답이지만, **3,981행 × 약 280 B ≈ 1.1 MB 는 통째로
> 메모리에 올라가는 크기**라 순차 스캔이 충분합니다. **필요해지기 전에 걸지 않습니다** —
> 행이 100배로 늘 일이 없는 테이블입니다.

| --- | ---: | ---: |

| **7일** | **27** | **0.68 %** |

**영업일당 약 5건입니다** (7일 27건 ÷ 영업일 5). 최근 30일의 일자별 분포도
`20260807` 4건 · `20260806` 5건 · `20260805` 4건 · `20260803` 9건으로 한 자릿수입니다.

> **이 실측이 배치 설계를 바꿉니다.** 전량 갱신이면 매일 3,982건(한도의 20 %)이지만,
> `modify_date` 증분이면 **약 6건 — 0.03 %** 입니다. **664배 차이**이고,
> 남는 한도를 F23 재무제표 조회 같은 실사용에 쓸 수 있습니다.
>
> **`synced_at` 은 변경된 행만이 아니라 확인된 행 전부에 찍습니다.** 증분 배치는
> 보통 0~5행만 건드리는데, 그 행만 갱신하면 **아무것도 안 바뀐 날 `max(synced_at)` 이
> 늙어 버려** 배치가 멈춘 것과 구별되지 않습니다. `corpCode.xml` 에 존재한 3,981행

> 그래야 `max(synced_at)` 이 **"배치가 마지막으로 성공한 시각"** 이 됩니다.
> 4.8절 `macro_series.updated_at` 과 같은 감시 지표입니다.

## 5. 마이그레이션 방침

### 5.1 왜 SQL 파일이 정본인가

Supabase 무료 플랜은 **백업 다운로드를 제공하지 않습니다**
([Production Checklist](https://supabase.com/docs/guides/deployment/going-into-prod),
[CN-001](../00-index/변경이력.md#cn-001) 기록). 프로젝트가 정지되거나 날아가면
대시보드에서 만든 스키마는 복구 수단이 없습니다.

**따라서 스키마의 정본은 git 안의 SQL 파일입니다.**
작업자 전역 규칙 8.1 의 "로컬이 정본" 과 같은 원칙입니다
(그 규칙은 저장소 밖 `~/.claude/CLAUDE.md` 에 있어 여기서 링크하지 않습니다).

### 5.2 파일 배치와 이름

```
supabase/
  migrations/
    20260809120000_init_types.sql          -- 2절 enum + 3절 확장
    20260809120100_init_user.sql           -- app_user
    20260809120200_init_recommendation.sql -- recommendation, recommendation_item
    20260809120300_init_combination.sql    -- combination_query
    20260809120400_init_simulation.sql     -- simulation_run, simulation_point
    20260809120500_init_backtest.sql       -- backtest_summary
    20260809120600_init_doc_chunk.sql      -- doc_chunk + hnsw + match_doc_chunk()
    20260810120000_init_macro.sql          -- macro_series, macro_observation + 초기 4행
    20260810120100_init_dart_company.sql   -- dart_company (4.9절)
    20260810120200_init_rls.sql            -- 6절 RLS 정책 일괄
    20260810120300_fix_rls_initplan.sql    -- 정책 22개의 auth.uid() 를 (select auth.uid()) 로
  seed.sql                                 -- 로컬 개발용 표본 데이터
```

- 파일명은 **`YYYYMMDDHHmmss_설명.sql`** (Supabase CLI 규약). 시각은 **KST 기준으로 적되
  내용상 순서만 지키면 됩니다.**
- **한 파일 = 한 관심사.** 위 11개는 서로 독립적으로 읽힙니다.
- **`init_macro` 는 `macro_series` 초기 4행까지 함께 넣습니다.** 스키마와 달리 이 4행은
  **참조 데이터**라 코드에 하드코딩할 것이 아니고, 없으면 배치가 돌 대상이 없습니다.
  KOSIS 행은 통계표가 정해진 뒤 **별도 마이그레이션**으로 추가합니다 (4.8절).
- **`init_dart_company` 에는 데이터를 넣지 않습니다.** `macro_series` 와 달리 3,981행은
  마이그레이션에 넣을 크기가 아니고, **배치가 처음 돌 때 채웁니다** (4.9절).
- RLS 를 `init_rls` 로 몬 것은 **모든 테이블이 존재한 뒤에 정책을 걸어야** 하기 때문입니다.
  뒤따르는 `fix_rls_initplan` 은 정책을 새로 만들지 않고 **조건식만 바꿉니다** (6.3절).

> **`init_rls` 의 시각을 `…120100` → `…120200` 으로 밀었습니다.** `dart_company` 가
> 그 앞에 들어가야 정책을 걸 대상이 존재합니다. 5.3 의 "적용한 마이그레이션은 수정하지
> 않는다" 를 어긴 것이 아닙니다 — **당시에는 아직 아무것도 적용되지 않았고**, 이 목록은
> 파일이 아니라 계획이었습니다. **지금은 11개 전부 원격에 적용됐으므로**(5.4절)
> 이 파일들은 더 이상 고치지 않습니다.

### 5.3 규칙

| 규칙 | 이유 |

## 6. RLS (행 수준 보안)

Supabase 는 **RLS 를 켜지 않으면 `anon` 키로 테이블 전체가 읽힙니다.**
공개 배포([CN-019](../00-index/변경이력.md#cn-019))가 전제이므로 필수입니다.

```sql
alter table app_user            enable row level security;
alter table recommendation      enable row level security;
alter table recommendation_item enable row level security;
alter table combination_query   enable row level security;
alter table simulation_run      enable row level security;
alter table simulation_point    enable row level security;
alter table backtest_summary    enable row level security;
alter table doc_chunk           enable row level security;
alter table macro_series        enable row level security;
alter table macro_observation   enable row level security;
alter table dart_company        enable row level security;
```

### 6.1 정책 요약

| 테이블 | SELECT | INSERT | UPDATE / DELETE |
| --- | --- | --- | --- |
| `app_user` | 본인만 (`(select auth.uid()) = id`) | 본인만 | 본인만 |
| 이력 4종 | 본인 행만 (`(select auth.uid()) = user_id`) | 인증 사용자: 본인 `user_id` 로만 | 본인만 |
| `recommendation_item` · `simulation_point` | 부모 행이 보이면 보임 | 서버 경유만 | 금지 |
| `doc_chunk` | **누구나 SELECT** | 서버 경유만 | 서버 경유만 |
| `macro_series` · `macro_observation` | **누구나 SELECT** | 배치(`service_role`)만 | 배치만 |
| `dart_company` | **누구나 SELECT** | 배치(`service_role`)만 | 배치만 |

> **참조 데이터 3종(`doc_chunk` · 거시지표 · 회사 마스터)은 공개 SELECT 입니다.**
> 사용자 데이터가 아니라 공개 통계·문서·공시정보이고, 숨겨서 얻을 것이 없습니다.
> **쓰기만 막으면 됩니다.**
>
> **`dart_company` 는 DART 가 이미 전부 공개한 값입니다.** `bizr_no`·`adres`·`phn_no`
> 까지 포함해 [DART 기업개황](https://dart.fss.or.kr/) 에서 누구나 조회할 수 있는
> **법인 공시정보**이고 개인정보가 아닙니다 (4.9절).

```sql
-- 예: 추천 이력 조회. auth.uid() 를 select 로 감싸는 이유는 6.3절.
create policy "본인 추천만 조회"
  on recommendation for select
  using ((select auth.uid()) = user_id);

-- 예: 문서 청크는 공개 지식이므로 읽기만 허용
create policy "문서 청크 공개 조회"
  on doc_chunk for select
  using (true);
```

### 6.2 비로그인 이력은 RLS 로 못 막습니다 — 정면으로 인정합니다

`anon_id` 는 브라우저가 보내는 값이라 **정책 조건으로 쓰면 아무나 남의 `anon_id` 를
넣어 조회할 수 있습니다.** RLS 로 해결되지 않습니다.

**대응**

1. 비로그인 이력은 **`anon` 키로 직접 조회하지 않습니다.** FastAPI 서버가
   **`service_role` 키로 대신 조회**하고, `anon_id` 는 요청 쿠키에서만 읽습니다.
2. 비로그인 이력에 **개인정보를 저장하지 않습니다** (티커·금액·기간뿐).
3. `service_role` 키는 **서버 환경변수로만** 둡니다. 프론트에 내려가면 RLS 가 전부 무력화됩니다.

> **남는 위험을 명시합니다.** 위 1번은 "서버를 믿는다" 는 전제입니다.
> 비로그인 이력의 기밀성은 **보장하지 않으며**, 그 사실을 화면에도 적습니다
> ([`../50-UI/화면-상세.md`](../50-UI/화면-상세.md) 에서 다룸).

### 6.3 `auth.uid()` 는 반드시 `(select ...)` 로 감쌉니다

**원격 적용 직후 성능 린터가 이것 하나로 22건을 올렸습니다** (2026-08-10 ·
[CN-095](../00-index/변경이력.md#cn-095)). 정책 조건에 맨몸으로 쓴 `auth.uid()` 는
플래너가 상수로 접지 못해 **행마다 다시 평가됩니다.** `(select auth.uid())` 로 감싸면
InitPlan 으로 **한 번만** 평가되고 결과가 재사용됩니다.

```sql
-- ✗ 행마다 평가
using (auth.uid() = user_id)

-- ✓ 요청당 한 번
using ((select auth.uid()) = user_id)
```

**판정 결과는 달라지지 않습니다.** `auth.uid()` 는 요청 단위로 고정된 값이라 한 번
읽든 행마다 읽든 같습니다. 실제로 `alter policy` 전후로 `anon` 가시성 실측이
동일했습니다 (5.4절 표의 "RLS 실동작" 을 두 번 돌렸습니다).

출처: [Supabase — RLS 성능 · Call functions with select](https://supabase.com/docs/guides/database/postgres/row-level-security#call-functions-with-select)
(2026-08-10 확인)

> **앞으로 정책을 새로 쓸 때도 이 형태로 씁니다.** 위 6.1절 예시 SQL 도 그렇게 고쳤습니다.
> `using (true)` 인 공개 조회 4종은 auth 함수를 부르지 않아 대상이 아닙니다.
