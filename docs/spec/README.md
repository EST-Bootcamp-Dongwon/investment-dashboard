## 2. 문서를 쓰는 규칙

### 2.1 기능 ID 는 절대 재사용하지 않는다

모든 기능에는 `F01` ~ `F29` 형태의 **영구 ID** 가 붙습니다.
기능이 폐기돼도 ID 는 회수하지 않고 `폐기` 상태로 남깁니다.
새 기능은 항상 가장 큰 번호 다음을 씁니다. 대장은
[`00-index/기능ID-대장.md`](00-index/기능ID-대장.md) 한 곳뿐입니다.

번호 공간은 셋입니다 — `F##` 제품 기능(29개) · `A##` 아카이브(8개) ·
`X##` 폐기(5개). **서로 겹치지 않습니다.**

### 2.2 근거 없는 문장을 쓰지 않는다

명세에 적는 숫자·동작·제약은 아래 셋 중 하나여야 합니다.

1. **코드에서 확인** — 파일과 줄 번호를 함께 적는다. 예: `app/backend/main.py:1167`
2. **실측** — 명령과 측정일을 함께 적는다. 예: `docker system df` 기준 2026-08-07
3. **공식 문서** — URL 과 확인일을 함께 적는다.

셋 다 아니면 **`(확인 필요)`** 를 붙입니다. 추측을 사실처럼 적지 않습니다.

### 2.3 버전은 작업 중에 올리지 않는다

이게 이 폴더의 가장 중요한 운영 규칙입니다.

- **작업 중에는 버전을 올리지 않습니다.** 스펙이 바뀌면
  [`00-index/변경이력.md`](00-index/변경이력.md) 의 **"미반영 변경노트"** 절에 한 줄로 쌓아둡니다.
- **마일스톤(기능 1개·스프린트 1회)이 끝나면 그때 한 번에** 버전을 올립니다.
  이때 전체 명세서 + 요약본 + 변경사항을 동시에 갱신하고,
  ERD ↔ API ↔ 기능명세 ↔ UI 의 정합성을 함께 검증합니다.
- 올리는 폭:
  - **Major (+1.0)** — 아키텍처·데이터 모델이 바뀐다. 기존 문서를 다시 읽어야 한다.
  - **Minor (+0.1)** — 기능·엔드포인트가 늘거나 준다. 읽던 사람은 델타만 보면 된다.
  - **오탈자·서식** — 버전을 올리지 않는다.

> 왜 이렇게 하나: 작업 중에 버전을 올리면 v2.1 이 하루에 다섯 번 생기고,
> "지금 어느 버전이 정본인지" 를 아무도 모르게 됩니다.

### 2.4 문서마다 머리말을 단다

```markdown
> - **버전**: v2.1
> - **최종 수정**: 2026-08-10 (KST)
> - **상태**: 초안 | 검토중 | 확정
> - **관련**: [기능ID-대장](../00-index/기능ID-대장.md) F05, F06
```

## 3. 이 폴더가 색인에 걸리지 않는 이유

이 저장소의 RAG 색인 스크립트는 `docs/*.md` 를 **비재귀로** 훑습니다
(`scripts/upload_docs_to_qdrant.sh:137`). 그래서 `docs/spec/` 아래 문서는
Qdrant 색인에 들어가지 않습니다.

명세서를 RAG 챗(F27)에서 검색하게 만들고 싶다면 그 스크립트를 고쳐야 합니다.
지금은 **의도적으로 색인하지 않습니다** — 명세서와 학습 자료가 섞이면
챗 답변의 출처가 흐려지기 때문입니다.

## 4. 폴더와 파일 이름 규칙

- 폴더: `NN-분류` (두 자리 숫자 + 한국어). 정렬 순서가 곧 읽는 순서.
- 파일: 한국어 명사구, 공백 대신 하이픈. 예: `개념설명-모달-사양.md`
- 기능 문서는 도메인 단위로 묶습니다. 기능 1개당 파일 1개로 쪼개지 않습니다
  (27개 파일이 되면 아무도 안 읽습니다).
